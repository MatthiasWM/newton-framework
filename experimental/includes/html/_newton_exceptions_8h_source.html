15/****************************************************************************************
16
17 There are several kinds of exceptions we can support:
18
19 newtonStyleExceptions
20 ...based on setjmp/longjmp, with the exceptions thrown being
21 "structured strings". Can be used to build any standalone system
22 with a 2.1 C++ compiler.
23
24 cppStyleExceptions
25 ...based on C++ keywords, with the exceptions thrown being arbitrary
26 data types, usually objects of CNewtonException or a subclass. Can be
27 used to build any standalone system with a 3.0 C++ compiler.
28
29 afxStyleExceptions
30 ...integrates with MFC's exception system, with the exceptions being
31 objects of CException or a subclass (of which CNewtonException is one).
32 If _AFX_OLD_EXCEPTIONS is defined, use the variation of this that works
33 with setjmp/longjmp; else use the variation that works works with keywords.
34
35 macappStyleExceptions
36 ...integrates with MacApp's exception system. Not yet implemented.
37
38 sehStyleExceptions
39 ...based on Win32's Structured Exception Handling. (not yet implemented, if
40 ever).
41

73
74 Exceptions are declared and defined using the DeclareException and
75 NewDefineException macros. Both macros take the exception name as the
76 first parameter and the exception's superclass as the second parameter.
77 NewDefineException also takes a "structured string" as a third
78 parameter to enforce a hierarchy under exception systems that can't
79 work with C++ classes.
80
81 DeclareException(exMyException, exRootException)
82 NewDefineException(exMyException,exRootException,evt.ex.myException)
83
84 An exception is signalled with the throw1, throw2, and throw3 macros.
85 The throw1 macro takes an exception name and throws it in the manner
86 appropriate to the underlying exception system being used.
87
88 throw1(exMyException);
89
90 The throw2 macro takes an arbitrary data value as a second parameter.
91 This data can be used to aid in debugging. For instance, it could
92 contain an error code.
93
94 throw2(exMyException, 1234);
95
96 If the data you are throwing is heap data that needs to be disposed of
97 after the exception has been handled, you can use the throw3 macro and
98 specify a destructor function.
99
100 throw3(exMyException, myHeapData, DestroyHeapDataFn);
101
102 There is a Throw function, which takes three arguments: an exception
103 name, a void* for accompanying data, and a pointer to a deallocation
104 function for the data (NULL for none).
105
106 Throw(exMyException, (void*) 1234, 0);
107
108 In C++. the second and third arguments default to zero, so you can just
109 say
110
111 Throw(exMyException);
112
113 WARNING: When running under a system that supports throwing and catching
114 exceptions based on data type, the Throw function will attempt to
115 convert the exception name (the first parameter, which is a string) to
116 an object of the appropriate type. It does this by comparing the
117 exception name against all known exception types. This process can make
118 the Throw function slow (because of the comparisons that are required)
119 or faulty (if the exception name doesn't correspond to any of the
120 known exception types). For these reasons, use of the Throw function is
121 discouraged. Instead, use the throw1, throw2, and throw3 macros
122 whenever you can.
123
124 There is ThrowMsg function that takes a char* and throws an
125 exMsgException with the given string as the data. This is good for
126 random debugging messages.
127
128 ThrowMsg("Random debugging message");
129
130 Exception handlers are introduced with newton_try and ended with
131 end_try. Within a handler are newton_catch clauses that specify the
132 exception names they handle. A newton_catch clause will catch the
133 specified exception or any of its subexceptions. Inside a newton_catch
134 clause, the current exception can be accessed with CurrentException().
135
136 newton_try
137 {
138 DoSomeStuff;
139 }
140 newton_catch (exBlahError)
141 {
142 printf("Couldn't do stuff: %s.", CurrentException()->name);
143 }
144 end_try;
145
146 A newton_catch clause can throw the current exception again using
147 the rethrow macro.
148
149 newton_catch (exBlahError)
150 {
151 blahErrors++;
152 rethrow;
153 }
154
155 A newton_catch_all clause may appear after the newton_catch clauses (if
156 any). If no newton_catch clause matches the current exception, the
157 newton_catch_all clause will catch the exception.
158
159 TSomething foo;
160
161 newton_try
162 {
163 DoSomeStuff;
164 }
165 newton_catch (exBlahError)
166 {
167 printf("Couldn't do stuff: %s.", CurrentException()->name);
168 }
169 newton_catch_all
170 {
171 exception_occurred = true;
172 }
173 end_try;
174
175 A cleanup clause may appear after the newton_catch clauses (if any). If
176 no newton_catch clause matches the current exception, the cleanup
177 clause will be run before the next handler is tried. This makes cleanup
178 clauses identical to newton_catch_all clauses, except that cleanup
179 clauses implicitly rethrow the exception.
180
181 TSomething foo;
182
183 newton_try
184 {
185 DoSomeStuff;
186 }
187 cleanup
188 {
189 foo.~TSomething();
190 }
191 end_try;
192
193 If the compiler being used doesn't provide the appropriate support, you
194 have to call destructors yourself in cases like the above. Of course,
195 this is error-prone. You can determine if the compiler you're using
196 destructs objects when unwinding the stack by using the
197 hasAutoDestructOnException preprocessor symbol. Thus, your exception
198 handling code could look like:
199
200 TSomething foo;
201
202 #if !defined(hasAutoDestructOnException)
203 newton_try
204 #endif
205 {
206 DoSomeStuff;
207 }
208 #if !defined(hasAutoDestructOnException)
209 cleanup
210 {
211 foo.~TSomething();
212 }
213 end_try;
214 #endif
215
216 Finally, the unwind_protect construct allows the specification of code
217 that must be run whether or not an exception occurs.
218
219 unwind_protect
220 {
221 OpenAFile();
222 DoSomethingWithTheFile();
223 }
224 on_unwind
225 {
226 CloseTheFile();
227 }
228 end_unwind;
229
230 Within an on_unwind block, you can determine whether an exception
231 occurred by using unwind_failed(). If an exception occurred, it will
232 automatically be rethrown at the end of the on_unwind clause.
233
234 Sometimes you may need to combine unwind_protect with try/catch:
235
236 newton_try
237 {
238 unwind_protect
239 {
240 OpenAFile();
241 DoSomethingWithTheFile();
242 }
243 on_unwind
244 {
245 CloseTheFile();
246 }
247 end_unwind;
248 }
249 newton_catch (exMyError)
250 {
251 printf("Couldn't DoSomethingWithTheFile!");
252 }
253 end_try;
254
255 CAUTION
256
257 There is a subtle problem that can occur when the compiler assigns local
258 variables to registers. If you modify the variable inside of a try
259 block preceding code that could possibly throw an exception, and you
260 need to access that variable after the try block has exited, you must
261 declare that variable as volatile. Example:
262
263 DECLARE_VOLATILE(int, x);
264 x = 0;
265 newton_try
266 {
267 ...
268 x = 1;
269 ... exception thrown here ...
270 }
271 newton_catch (exMyError)
272 {
273 ...x... // x used here...
274 }
275 end_try;
276
277 ...x... // ... and/or x used here.
278
279
280 If you don't declare x as volatile, it might be kept in a register. When
281 the exception is thrown, the state of the register is restored to the
282 value it had when the try block was entered. Thus, x would hold 0 instead
283 of 1 like we expected.

286 USAGE NOTES FOR MACAPP CLIENTS:
287
288 The newton_try/newton_throw/end_try/etc. macros have been redefined in
289 terms of the MacApp functions the provide failure handling. This means
290 that Newton code that uses these macros will raise signals in the MacApp
291 style, and that Newton code and MacApp code will be speaking on the same
292 level.
293
294 Normal MacApp failure handling looks like:
295
296 FailInfo fi;
297
298 Try(fi)
299 {
300 // Execute some code that might throw an exception.
301 fi.Success();
302 }
303 else
304 {
305 // Handle the exception here.
306 if (fi.error == kNewtonException)
307 {
308 Exception* e = (Exception*) fi.message;
309 printf("Couldn't do stuff: %s.", e->name);
310 delete e;
311 }
312 else
313 {
314 }
315 fi.ReSignal(); // optional
316 }
317
318 When a Newton exception reaches the "else" clause, fi.error will hold
319 kNewtonException and fi.message will hold a pointer to an Exception
320 record. Note that this record has been allocated dynamically on the
321 heap, so it's up to you to delete it.
322
323 If you like, you could retrofit your MacApp code to use the Newton
324 macros. By doing this, you gain the following benefits:
325
326 - Richer set of semantics (can use unwind_protect and can catch
327 exceptions with newton_catch or newton_catch_all.
328 - You won't have to remember to delete the Exception object.
329 - You don't have to create a FailInfo variable.
330
331 Thus, you could perform exception handling as:
332
333 newton_try
334 {
335 // Execute some code that might throw an exception.
336 }
337 newton_catch(CNewtonException)
338 {
339 // Catch all Newton exceptions here
340 // Access Exception data with CurrentException()
341 }
342 newton_catch_all
343 {
344 // Catch all MacApp errors here
345 // Access "error" and "message" via hidden _info variable.
346 }
347 end_try;

350 USAGE NOTES FOR MFC CLIENTS:
351
352 The newton_try/newton_throw/end_try/etc. macros have been redefined in
353 terms of the MFC functions that provide exception support. This means
354 that Newton code that uses these macros will throw MFC-style
355 exceptions, and that Newton code and MFC code will be speaking on the
356 same level. The kinds of exceptions that Newton throws are implemented
357 as subclasses of CException, the base class for all exceptions thrown
358 in MFC.
359
360 Normal MFC try/catch blocks look like this:
361
362 TRY
363 {
364 // Execute some code that might throw an exception.
365 }
366 CATCH (CException, e)
367 {
368 // Handle the exception here.
369 // "e" is a pointer to an exception of type CException.
370 // MFC will automatically take care of deleting the
371 // CException object if needed.
372 }
373 END_CATCH // END_CATCH will rethrow any uncaught exceptions;
374 // use END_TRY to silently swallow them.
375
376 Multiple exception catching looks like this:
377
378 TRY
379 {
380 // Execute some code that might throw an exception.
381 }
382 CATCH (CMemoryException, e)
383 {
384 // "e" is a pointer to an exception of type CMemoryException
385 }
386 AND_CATCH (CFileException, e)
387 {
388 // "e" is a pointer to an exception of type CFileException
389 }
390 AND_CATCH (CException, e)
391 {
392 // catch all exceptions
393 }
394 END_CATCH
395
396 Newton exceptions are implemented as sub-classes of CException. The name
397 of the subclass is the result of string-izing the exception name with
398 "Class". Thus, to catch exMsgException:
399
400 TRY
401 {
402 // Execute some code that might throw an exception.
403 }
404 CATCH (exMsgExceptionClass, e)
405 {
406 // Print the message
407 printf("Exception message: %s\n", (char*) e->fException.data)
408 }
409 AND_CATCH (CException, e)
410 {
411 // catch any other exceptions
412 }
413 END_CATCH
414
415 All Newton exceptions are subclasses of CNewtonExceptionClass, which is
416 a subclass of CException. CNewtonExceptionClass contains a public
417 fException data member which is an Exception struct. You can therefore
418 access the name and/or data fields via fException.
419
420 TRY
421 {
422 // Call some Newton ROM code.
423 }
424 CATCH (CNewtonExceptionClass, e)
425 {
426 printf("Couldn't do stuff: %s.", e->fException.name);
427 }
428 END_CATCH
